# LLM Consortium — Detailed Implementation Plan

> **Goal:** Build a fully configurable, observable, reproducible experiment pipeline that
> executes 8 consortium variants × 8 design tasks × 5 repetitions = 320 runs, evaluates
> every output via LLM-based rubric scoring, and culminates in generating
> **Section 10.2 — The Practitioner Decision Framework**.

## 3. Configuration Architecture

**Principle: Zero hardcoded values.** Every parameter that could change between runs — model
names, temperatures, token limits, retry counts, agent counts, round counts, rubric weights —
lives in YAML config files. The code reads config; it never contains magic numbers.

### 3.1 Experiment Config (top-level)

```yaml
# configs/experiment.yaml
experiment:
  name: "llm-consortium-v1"
  seed: 42                          # for reproducibility
  output_dir: "data/"
  database: "data/consortium.db"
  
  # Which variants to run (comment out to skip)
  variants:
    - v1_baseline
    - v2_leader_reviewers
    - v3_parallel_merge
    - v4_adversarial
    - v5_specialist_panel
    - v6_rotating_leader
    - v7_consensus
    - v8_structured_debate
  
  # Which tasks to run
  tasks:
    - t1_url_shortener
    - t2_chat_app
    - t3_ecommerce
    - t4_notification
    - t5_trading_platform
    - t6_video_streaming
    - t7_autonomous_fleet
    - t8_ml_platform

  repetitions: 5                    # runs per (variant, task) pair
  
  # Default model assignments (overridable per-variant)
  defaults:
    designer_model: "gpt-4.1"       # resolves to configs/models/openai_gpt4_1.yaml
    reviewer_model: "gpt-4.1"
    evaluator_model: "sonnet-4.5"   # resolves to configs/models/anthropic_sonnet.yaml
  
  # Batch API settings
  batch:
    enabled: true                   # use batch APIs where available
    max_concurrent_batches: 5
    poll_interval_seconds: 60
    fallback_to_realtime: true      # if batch fails, retry in real-time
  
  # Global safety limits
  limits:
    max_tokens_per_run: 500_000     # hard abort if a SINGLE run exceeds this
    max_cost_per_run_usd: 2.00      # hard abort per SINGLE run (not total experiment)
                                    # Most expensive single run: v3/v7/v8 with GPT-4.1
                                    # ≈ $0.88 gen + $0.14 eval = ~$1.02.
                                    # $2.00 gives 2× headroom for retries/overhead.
                                    # This is a circuit breaker — if a single run
                                    # hits $2 something is wrong (infinite loop, etc.)
    max_total_cost_usd: 500.00      # hard abort for ENTIRE experiment
                                    # Expected: ~$400 (GPT-4.1 gen + Sonnet eval + batch)
                                    # $500 gives headroom for pilot + retries
    max_retries: 3
    retry_backoff_base: 2.0         # exponential backoff: 2^attempt seconds
    timeout_seconds: 300            # per-call timeout
```

### 3.3 Variant Config

Each variant config defines the agent topology, workflow, and all tuning knobs.

```yaml
# configs/variants/v2_leader_reviewers.yaml
variant:
  id: "v2"
  name: "Leader + Reviewers"
  description: "Centralized × Homogeneous × Cooperative"
  matrix_position:
    authority: "centralized"
    roles: "homogeneous"
    dynamics: "cooperative"
  
  # Sub-variant selection (v2a, v2b, v2c)
  sub_variant: "v2a"                    # v2a=same-model, v2b=cross-model, v2c=panel
  
  # Agent definitions — each agent references a model config by id
  agents:
    leader:
      role: "designer"
      model: "gpt-4.1"                 # override experiment default if needed
      system_prompt_template: "generation/design_system.j2"
      parameters:                       # agent-level param overrides
        temperature: 0.7
    
    reviewers:
      count: 2                          # number of parallel reviewers
      role: "reviewer"
      model: "gpt-4.1"                 # for v2b, set to different model
      system_prompt_template: "review/general_review.j2"
      parameters:
        temperature: 0.5                # reviewers can be less creative
  
  # Workflow parameters
  workflow:
    max_rounds: 3                       # leader-review cycles
    include_rubric_in_prompt: true      # whether agents see the evaluation rubric
    reviewer_sees_other_reviews: false  # independent reviews
    
  # Token budget for this variant
  token_budget:
    estimated_input: 70_000
    estimated_output: 40_000
```

Every variant's prompt sequence is defined in its YAML config (`configs/variants/vN_*.yaml`)
via the `agents` and `workflow` sections. The variant orchestrator code reads the config

### 4.2 Provider Protocol

```python
# src/consortium/providers/base.py
from __future__ import annotations

import abc
from dataclasses import dataclass, field
from datetime import datetime

@dataclass(frozen=True)
class LLMRequest:
    """Immutable request to an LLM."""
    system_prompt: str
    messages: list[dict[str, str]]        # [{"role": "user", "content": "..."}]
    model_config_id: str                  # references a model config
    parameters: dict[str, object] = field(default_factory=dict)
    metadata: dict[str, str] = field(default_factory=dict)  # for tracing
    
@dataclass(frozen=True)
class LLMResponse:
    """Immutable response from an LLM."""
    content: str
    model: str                            # actual model string returned by API
    input_tokens: int
    output_tokens: int
    latency_ms: float
    cost_usd: float                       # computed from model pricing config
    timestamp: datetime
    request_id: str                       # provider's request ID
    cached_input_tokens: int = 0          # tokens served from cache
    batch_id: str | None = None           # if served via batch API
    metadata: dict[str, str] = field(default_factory=dict)

class LLMProvider(abc.ABC):
    """Protocol for all LLM providers."""
    
    @abc.abstractmethod
    async def complete(self, request: LLMRequest) -> LLMResponse:
        """Send a single real-time completion request."""
        ...
    
    @abc.abstractmethod
    async def complete_batch(self, requests: list[LLMRequest]) -> list[LLMResponse]:
        """Submit requests via batch API. Blocks until all results are ready."""
        ...
    
    @abc.abstractmethod
    def estimate_cost(self, input_tokens: int, output_tokens: int, batch: bool = False) -> float:
        """Estimate cost in USD for given token counts."""
        ...
    
    @abc.abstractmethod
    def supports_batch(self) -> bool:
        """Whether this provider supports batch API."""
        ...
```

### 4.3 Key Design Decisions

- **All LLM calls are `async`**: we use `asyncio` throughout, enabling parallel agent calls
  (e.g., v3's 3 parallel designers, v5's 3 specialist reviewers).
- **Provider instances are stateless**: they hold only config, not conversation state.
  Conversation history is managed by `RunContext`.
- **Every `LLMResponse` carries its own cost**: computed at creation time from model pricing
  config. No post-hoc cost estimation.
- **Retry logic lives in providers**: using `tenacity` with configurable backoff from model config.

### 5.3 Variant Orchestrator Pattern

```python
# src/consortium/orchestrator/variants/base.py
class VariantOrchestrator(abc.ABC):
    """Each variant implements this to define its multi-agent workflow."""
    
    def __init__(self, config: VariantConfig, agents: dict[str, BaseAgent]):
        self.config = config
        self.agents = agents
    
    @abc.abstractmethod
    async def execute(self, task: TaskConfig, context: RunContext) -> DesignArtifact:
        """Run the variant's complete workflow and return the final design."""
        ...

# Example: v2 implementation
class V2LeaderReviewers(VariantOrchestrator):
    async def execute(self, task: TaskConfig, context: RunContext) -> DesignArtifact:
        leader = self.agents["leader"]
        reviewers = self.agents["reviewers"]  # list
        
        # Step 1: Leader generates initial design
        design = await leader.generate_design(task, context)
        context.designs.append(design)
        
        for round_num in range(self.config.workflow.max_rounds):
            # Step 2: K reviewers critique in parallel
            reviews = await asyncio.gather(
                *[r.review(design, task, context) for r in reviewers]
            )
            context.reviews.extend(reviews)
            
            # Step 3: Leader revises based on all reviews
            design = await leader.revise_design(design, reviews, task, context)
            context.designs.append(design)
        
        return design
```

### 8.5 Implementation: Tracing Middleware

Tracing is implemented as a **provider wrapper**, not by modifying each provider:

```python
class TracingProvider(LLMProvider):
    """Wraps any LLMProvider to automatically record traces."""
    
    def __init__(self, inner: LLMProvider, context: RunContext, agent_meta: AgentMeta):
        self.inner = inner
        self.context = context
        self.agent_meta = agent_meta
    
    async def complete(self, request: LLMRequest) -> LLMResponse:
        started = datetime.now(UTC)
        response = await self.inner.complete(request)
        ended = datetime.now(UTC)
        
        trace = LLMCallTrace(
            trace_id=uuid4().hex,
            run_id=self.context.run_id,
            variant_id=self.context.variant_id,
            task_id=self.context.task_id,
            repetition=self.context.repetition,
            agent_role=self.agent_meta.role,
            agent_id=self.agent_meta.id,
            step=self.agent_meta.current_step,
            round=self.agent_meta.current_round,
            # ... all other fields from response ...
            started_at=started,
            ended_at=ended,
        )
        self.context.record_call(trace)
        return response
```

This means **every provider automatically gets tracing** with zero changes to agent or
orchestrator code.

### 9.2 Batch Execution Strategy

For the full 320-run experiment, we use **wave-based batching for BOTH generation AND
evaluation**. The key insight: within a single run, steps are sequential (review depends
on generation), but the SAME step across different runs is independent and batchable.

**Wave-Based Batching (Generation):**

Instead of running 320 runs one-at-a-time with real-time API calls, we batch by workflow
step across all runs:

```
Wave 1: Submit all 320 initial design generations as one batch
         → Wait for batch results (Anthropic/OpenAI: ~24h, Ollama: hours)

Wave 2: For runs needing review (v2/v4/v5/v6): submit all reviewer calls as a batch
         For v3/v7/v8: Wave 1 already produced K parallel designs (batched together)
         → Wait for batch results

Wave 3: Submit all revision calls (leader incorporates reviews) as a batch
         For v3: submit all merge calls as a batch
         → Wait for batch results

Wave 4: (if max_rounds > 1): repeat review + revise waves

Wave 5: All 320 final designs ready → submit 960 evaluator calls as one batch
```

**Why batch generation?** The 50% batch discount applies to ALL API calls, not just
evaluation. Batching generation saves ~$100 on a $400 experiment. The trade-off is
wall-clock time: batch APIs have ~24h turnaround vs. seconds for real-time. Since this
is a research experiment (not production), latency doesn't matter — cost does.

**Ollama batching:** Ollama has no server-side batch API, but `ollama_batch.py` implements
client-side concurrent request batching: submit N requests via async HTTP to the local
Ollama server, with configurable concurrency (default: 2, limited by GPU memory). This
isn't cheaper (already $0) but enables the same wave-based orchestration pattern.

**Fallback to real-time:** If `batch.fallback_to_realtime: true` (default), any failed
batch requests are retried via real-time API. The `--no-batch` CLI flag forces all calls
through real-time API for debugging.

```
Wave 1 (day 0–1):     Wave 2 (day 1–2):     Wave 3 (day 2–3):     Wave 4 (day 3–4):
┌───────────────┐    ┌───────────────┐    ┌───────────────┐    ┌───────────────┐
│ Batch: 320    │    │ Batch: ~480   │    │ Batch: 320    │    │ Batch: 960    │
│ initial gens  │───▶│ reviewer      │───▶│ revisions +   │───▶│ evaluator     │
│ (50% off)     │    │ calls         │    │ merges        │    │ calls         │
│               │    │ (50% off)     │    │ (50% off)     │    │ (50% off)     │
└───────────────┘    └───────────────┘    └───────────────┘    └───────────────┘

Total with batch discount: ~$200 (vs ~$400 real-time)
Total wall-clock: ~4 days (vs ~2 days real-time)
```

### 13.1 Framework Logic

The decision framework is generated by `consortium analyze --framework`. It works as follows:

```python
# src/consortium/analysis/framework.py

def generate_decision_framework(db: Database) -> DecisionFramework:
    """
    Generate the §10.2 practitioner decision framework from experiment data.
    
    For each (complexity_level, budget_priority, quality_priority) tuple:
    1. Filter results to matching complexity level
    2. Rank variants by quality (weighted rubric score median)
    3. Rank variants by cost-efficiency (quality / cost_usd)
    4. Apply budget constraint: if budget_priority = "low", exclude variants
       costing >1.5× the cheapest variant for that complexity level
    5. Select the Pareto-optimal variant that best satisfies the priority mix

    """
```
